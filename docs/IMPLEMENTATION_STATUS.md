# 구현 및 검토 보고 · 2026-09-17

확정된 요구사항의 프론트엔드·서버·인식·저장·오프라인 배포 코드를 구현했다. 현재 결과물은 **소프트웨어 검토 후보**이며 실제 장비 운전 승인 상태는 **NOT_VERIFIED**다. 사용자 요청대로 브라우저 실행, 프론트엔드 스크린샷, 화면의 직접 시각 검사는 수행하지 않았다.

## 검증 결과

검증 환경: 현재 Windows x64, Python 3.11.8, PyTorch 2.5.1+cpu, torchvision 0.20.1+cpu, timm 0.9.16, OpenCV 4.11.0.86, zxing-cpp 3.1.1. 새 `.venv-offline-verified`에 **--no-index**로 의존성을 설치하고 `pip check`를 통과했다.

- **기능 테스트 88개 통과**: 기존 실제 사진 인식, 헤지스 제공 127행 해독, 판정·계수·DB·권한·통신·복원·고장 경로 포함. 속도 한계 시험 9개는 별도 성능 항목으로 분리했다. [원본 결과](verification/functional-tests.xml)
- **마지막 운영 로직 테스트 49개 통과**: 최종 실물 필수 채널/작업 취소/저장 변경 후 재확인. 느린 실제 모델 테스트 1개는 앞의 기능 실행에서 통과했다. [원본 결과](verification/station-tests.xml)
- **프론트엔드 7개 통과**, TypeScript/프로덕션 빌드 통과. 목표 선택·바코드 선택성·옵션 편집·설정 잠금·복구 사유·권한·서버 readiness·요청 중 STOP 사용·수량 보정 중복 클릭 방지를 jsdom으로 검사했다. [결과](verification/frontend-tests.json)
- **실제 loopback HTTP/WebSocket 통합 통과**: 정적 JS/CSS, 초기 인증, RFID 작업/계수, 실시간 상태/heartbeat, DB 백업 다운로드, 미연결 장비 표시. 종료까지 확인했다. [결과](verification/local-http.json)
- 실제 PARSeq 로드/인식 테스트에서 network/torch.hub URL 경로를 차단한 상태로 통과했다. 모델 파일 112개 해시 검증과 소프트웨어 사전 검사 통과. [사전 검사](verification/preflight.json)
- 기존 인식 파일 12개 중 11개는 byte hash가 동일하다. `ocr/core.py`는 로컬 전용 로더로 변경했고 기존 Recognizer·추론·변환 함수 AST는 동일하다. [보존 검사](verification/legacy-preservation.json)
- npm audit의 확인 시점 취약점 **0건**. 사용하지 않는 Router/Zustand를 제거하고 테스트 도구를 수정 버전으로 고정했다. [audit 결과](verification/npm-audit.json), [Vitest 수정 근거](https://github.com/vitest-dev/vitest/security/advisories/GHSA-82fw-gwwq-j7x9)

### 통과로 표시하지 않은 성능 항목

전체 테스트 실행에서 기존 바코드 400ms 한계 시험은 한 사진이 **466ms**, 다른 전체 실행에서는 **423ms**로 실패했다. 단독 바코드 28개 테스트는 통과했지만 별도 반복 측정에서도 약 **242~477ms** 변동이 있었다. 따라서 전체 시험을 전부 통과했다고 표시하지 않는다. [전체 실행 결과](verification/pytest.xml), [반복 측정](verification/cpu-scheduling.json)

스레드 수만으로 원인이 해결된다는 근거가 없어 기존 알고리즘·스레드 설정·400ms 기준을 임의로 바꾸지 않았다. 현재 사용자 결정상 처리량·속도·takt는 미정이며, 이 항목은 실제 장비에서 공정 기준을 승인할 때 다시 측정한다. 이 CPU 결과로 Jetson의 시간 성능이나 목표 분당 처리량을 보장하지 않는다.

## 검토 중 발견해 수정한 주요 결함

- 중복/늦은 STOP이 현재 운전 상태와 충돌하던 경로, 정지 뒤 늦게 끝난 추론의 계수 가능성.
- 합격 후 일시정지/재개 시 중복 검사, 검사 위치에 있는 제품을 START로 먼저 움직이던 경로.
- 삭제한 메이커의 재시작 복원, 삭제 후 재등록 시 버전 이력 충돌.
- DB commit 실패 시 화면 계수와 영속 계수 불일치, Windows 백업 파일 핸들 유지.
- 시간 초과한 네이티브 검출 작업이 아직 실행 중인데 다음 검사를 시작할 수 있던 경로.
- chunked 요청 크기 제한 우회, 같은 운영 DB를 여러 서버가 열 수 있던 경로.

## 현장 투입 전 남은 조건

1. 사용자 보유 **제품 검출 라이브러리**의 실제 경로/함수/모델을 연결하고 해시를 고정해야 한다. 연결 계약과 차단 동작은 구현했지만 라이브러리 자체를 대신 만들지 않았다.
2. 실제 제품 간격·분당 처리량·속도·정지 안정화·센서/접촉기/배출 제한시간, OCR 영역·신뢰도·카메라 촬영값을 실측해야 한다.
3. J4012 BSP/JetPack·ARM64/CUDA/GStreamer OpenCV 조합과 libgpiod 설치 묶음을 장비 기준으로 확정해야 한다. Windows CPU 묶음은 Jetson 설치물이 아니다.
4. 물리 START 관측, J2 출력 극성, K0/KM2/정지 회로, 전원 복구·프로세스 강제 종료·OS 정지의 실제 OFF를 검증해야 한다.
5. RFID 명령서/응답 캡처로 실제 YRM 리더 프로토콜을 대조해야 한다. 문서에 없는 추가 명령의 가정을 실기 검증 없이 승인하지 않는다.
6. 메이커별 실제 기준표, 이미지 보존 정책, 현장 1,000건·8시간 이상 인수 시험 및 가능 시 72시간 시험이 남아 있다.
7. 사용자 요청으로 보류한 **브라우저 시각 검토**가 남아 있다.

이 조건들은 임의 값으로 승인 처리하지 않았다. 기본 REPLAY에서만 검토하며 HARDWARE 운전은 준비 조건을 만족할 때까지 차단한다. 상세 시험은 [HARDWARE_ACCEPTANCE.md](HARDWARE_ACCEPTANCE.md)를 따른다.

## 사용자 검토 및 파일

프로젝트 루트의 `run-station.ps1`은 서버만 실행한다. 사용자가 원할 때 로컬 화면을 열어 [OPERATIONS.md](OPERATIONS.md)의 검토 순서로 확인하면 된다. 배포 파일은 `release/txrx-0.3.0-windows-offline.zip`, 파일 해시는 `release/SHA256SUMS.txt`에 기록한다. 이 ZIP은 로컬 고객 기준 데이터를 포함하므로 로컬 배포용이다.

Git origin은 요청한 `https://github.com/puter1234/TxRx-1.git`으로 연결했다. 소스는 로컬 commit으로 보관하고 원격 push는 수행하지 않는다. 고객 전체 JSON/사진/모델 가중치/실행 데이터/환경/배포 ZIP은 Git에서 제외한다. 원본 G: 디렉터리는 변경하지 않았다.

사용량은 작업 10회마다 **잔여 사용량**으로 확인했다. 10/20/30/40/50/60/70/80/90회 확인은 각각 87/86/84/83/82/82/81/80/79%였다. 잔여 50% 제한을 넘지 않았다. 리셋 크레딧은 사용하지 않았다.
